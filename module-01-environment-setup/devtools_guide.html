DevTools as a Weapon

Every browser ships an attack console for free. Right-click almost anything and choose Inspect, or press F12. Five panels matter for XSS work. Learn what each one reveals before you write a single payload — half of finding an XSS bug is reading what the page is already telling you.

1. Elements — the live, rendered DOM

This is not "view source." View-source shows the HTML the server sent. Elements shows the DOM after the browser's parser and any JavaScript have finished mutating it — which is what actually executes. A payload can be invisible in view-source (because JS injected it after load) and fully present here.

Attacker use: double-click any element's text or attribute to edit it live. This only affects your own local view (nothing is sent to the server) — but it's exactly how you prototype "if I could get my string into this attribute, would it execute?" before you find the real injection point.
Try it: go to Site A, open Elements, find the <button id="btn-same"> element, double-click its text, and change it. Nothing breaks, nothing is saved — it's your sandbox.

2. Console — arbitrary JavaScript, in the page's own context

Anything you type into Console runs with the exact same privileges as the page's own scripts: same cookies (except HttpOnly ones — more in Module 15), same localStorage, same ability to make requests as "you."

Try these on Site A's console right now: 
document.domain
document.cookie
window.location.origin
document.querySelectorAll('script').length
Attacker use: this is your payload-development REPL. Before you ever inject a string into a real form field, you write and test the exact JavaScript here. alert(1) is the traditional "proof it runs" payload precisely because it's unmistakable and harmless — you'll use it constantly through this course.

3. Network — every request, every header, every byte

Reload Site A with Network open (checkbox "Preserve log" is useful) and click on the page's own request. Look at:

What to checkWhy it matters for XSS
Content-Type response headerIf it's not text/html, browsers generally won't execute script even if HTML is in the body — this is why servers sometimes set this deliberately as a defense.
Content-Security-Policy headerTells you upfront which of the 5 execution mechanisms (Module 03) are even allowed to fire. You'll read these constantly from Module 17 onward.
Set-Cookie flags (HttpOnly, Secure, SameSite)HttpOnly means JS — including your injected payload — cannot read that cookie via document.cookie. It changes what an XSS bug can actually steal.
Response body of a failed cross-origin fetchThe request often still fires and the server still answers — Network shows you the real response even when SOP hides it from your JavaScript. This gap (network-level visibility vs. script-level visibility) matters throughout the course.

4. Application — storage, cookies, service workers

Application → Storage shows Cookies, Local Storage, Session Storage for the current origin, scoped exactly the way your JavaScript is scoped. If your own script can't read a cookie here because it's HttpOnly, an XSS payload running as that script can't either — this panel tells you the ceiling of what a stolen-cookie attack can achieve before you even try it (Module 15).

5. Sources — breakpoints inside someone else's JavaScript

Set a breakpoint, and step through code line by line, inspecting variables as they're assigned. This is how you find DOM XSS sinks (Module 09) in real applications: you don't guess where innerHTML is being set with attacker data — you put a breakpoint on the property and watch the call stack tell you.

Try it later (Module 09): in Chrome, Sources → right side panel → Event Listener Breakpoints → expand DOM Mutation and check the boxes. Now any script that mutates the DOM will pause execution right there.
