Site A DevTools Guide

Module 01 — Tutorial

Goal: get the lab running, prove the Same-Origin Policy to yourself with your own eyes, and get comfortable in DevTools before Module 02 starts breaking the HTML parser on purpose.

Step 1 — Python environment

You need Python 3.9+ on your machine. Check:

python --version

Create an isolated environment inside this module's folder so course dependencies never touch your system Python:

# Windows (PowerShell or cmd)
cd module-01-environment-setup
python -m venv venv
venv\Scripts\activate
pip install -r requirements.txt

# macOS/Linux
cd module-01-environment-setup
python3 -m venv venv
source venv/bin/activate
pip install -r requirements.txt
Expected output: pip reports Successfully installed flask-3.0.3 ... (plus Flask's own dependencies: Werkzeug, Jinja2, click, itsdangerous, blinker).

Step 2 — run the lab

python lab_server.py
Expected output: 
================================================================
 Module 01 lab is up.
 Site A (main app) : http://127.0.0.1:5000
 Site B (other origin) : http://127.0.0.1:5001
 Open Site A in your browser and follow /tutorial
================================================================
 * Serving Flask app 'site_a'
 * Running on http://127.0.0.1:5000
If you instead see OSError: [Errno 98] Address already in use, something else on your machine is already listening on 5000 or 5001 — close it, or edit the ports in lab_server.py.

Step 3 — the same-origin / cross-origin experiment

  1. Open http://127.0.0.1:5000 in your browser.
  2. Open DevTools (F12), Console tab.
  3. Click fetch('/secret') — same origin. You should see JSON with a balance field print into the black box on the page.
  4. Click fetch('http://127.0.0.1:5001/secret') — cross origin. You should see an error message on the page, and in the Console a red error mentioning CORS or Access-Control-Allow-Origin.
  5. Switch to the Network tab, click the request row for secret that went to port 5001. Look at its Response sub-tab — the server's actual JSON is sitting right there, fully delivered over the network. Your JavaScript still isn't allowed to touch it. That gap between "the bytes arrived" and "your script can read them" IS the Same-Origin Policy — a browser-side rule enforced after the network layer, not a server-side one.

Step 4 — read the response headers

Still in Network, click the request to 127.0.0.1:5000/secret and look at Response Headers. Note there's no Access-Control-Allow-Origin header — Site A never granted permission for cross-origin script reads, so by default, none exist. This default-deny is the whole security model. (CORS is the mechanism a server uses to opt in to allowing specific cross-origin reads — you'll see that used, and abused, in later modules.)

Exercises before Module 02

  1. Change the port of Site B in lab_server.py to 5000 (same as Site A) temporarily, restart, and try to run both — what happens, and why does that prove ports alone define origin distinctness?
  2. Add a third route to Site A, /whoami, that returns jsonify({"origin": request.host_url}). Hit it from the browser address bar directly, then fetch it from Site B's console (open http://127.0.0.1:5001/, open its own DevTools, and try fetch('http://127.0.0.1:5000/whoami') from there). Confirm the block is symmetric — it doesn't matter which "direction" the fetch goes.
  3. Read one real CSP header. Visit any large real site (in a normal tab, just browsing — no attack traffic involved), open Network, and find its Content-Security-Policy response header. Paste it somewhere and try to identify one directive by name (e.g. script-src, default-src). You'll fully understand these by Module 17 — for now, just notice they exist in the wild.
Before Module 02: you should be able to state, from memory, what the three components of an origin are (scheme, host, port) and describe what you watched the browser refuse to do. Module 02 starts pulling apart how the browser turns HTML text into the DOM you were just inspecting — and why that process is forgiving of broken input in ways that become exploitable.
