# sparkbench

## Safety and scope

This is an authorized, localhost-only security research lab, not a toolkit for testing anyone else's systems. Every lab server here binds to `127.0.0.1` and stays there. See [SAFETY.md](SAFETY.md) for the full rules, but the short version, in my own words from that document, is this:

> Never point these payloads at a site you don't own or don't have written authorization to test... The moment you try a technique from this course against a real, third-party site without authorization, you've left "PhD security research" and entered unauthorized computer access.

No server in this repository is meant to bind to anything but localhost, no module asks you to touch a host other than `127.0.0.1`, and none of the "victim" data (cookies, tokens, balances) is real. It's synthetic, generated by the lab code itself.

## What this is, and what it isn't

`sparkbench` is the first-draft scratch version of an attack-first, defense-later XSS course: make a real script execute in a real browser through a specific mechanism, then study the defense that actually closes it, not one that just looks like it does. I planned the full curriculum as 19 modules built around a five-mechanism taxonomy (tag parsing, event-handler attributes, URI schemes, DOM sinks, context-escape/mXSS) meant to cover the entire documented XSS attack surface.

This repository is not the finished course. It's the early prototype where I worked out the shape of the curriculum, the module packaging convention, the Head First-style teaching approach, the safety scaffolding, on Module 01 before building the rest. `breachlab` is the sibling repository where I finished all 19 modules. Treat this repo as its historical first draft, kept for the record of how I designed the format, not as a working alternative to it.

## Module packaging convention

The convention I established here, and carried forward into `breachlab`, gives every module the same shape: `headfirst.md` explains the concept Head First-style, loud, visual, repetitive on purpose, with self-test call-outs. `tutorial.html` is the hands-on walkthrough. `DECISIONS.md` explains why the lab code is built the way it is, kept separate from the security concept itself. There's working code (`lab_server.py`, attack HTML pages, `requirements.txt`), and a `run.bat`/`Makefile` for one-command launch.

## Tech stack

Module 01 in this prototype is Python/Flask only (`lab_server.py`, single process, runs two origins through a background thread to demonstrate same-origin policy). It doesn't yet have the dual Python/Node implementation that `breachlab` later adopted. That pattern came after this scratch build.

## Running Module 01

```bash
cd module-01-environment-setup
pip install -r requirements.txt
python lab_server.py
```

Follow the printed URLs. The module spins up two origins on localhost to demonstrate same-origin policy before anything else happens.
